# Hybrid 텍스트 제거 시스템 구현 계획 (Gemini + LaMa CPU)

## 1. 개요 및 목표

본 문서는 `make_slide` 프로젝트의 텍스트 제거 품질을 획기적으로 개선하기 위한 **[Hybrid 방식: Gemini 감지 + LaMa(CPU) 복원]**의 단계적 구현 계획을 기술합니다.

**핵심 목표**:

1.  **감지(Detection)**: 현존 최강의 `Gemini 3.0 Flash`를 유지하여 모든 텍스트 요소를 정확히 포착.
2.  **복원(Inpainting)**: 기존 `OpenCV`의 한계(블러 현상)를 극복하기 위해 `LaMa` 딥러닝 모델을 도입하되, 초기 비용 절감을 위해 **로컬 CPU 환경**에 최적화하여 포팅.

---

## 2. 왜 이 방식(Hybrid CPU)인가? (선정 근거)

### 2.1 기존 방식 및 대안과의 비교

| 구분          | **시나리오 A** (오픈소스 조합) | **시나리오 B** (완전 AI) | **현재 방식**       | **✅ Hybrid CPU (제안)** |
| :------------ | :----------------------------- | :----------------------- | :------------------ | :----------------------- |
| **감지 기술** | EasyOCR (보통)                 | EasyOCR (보통)           | **Gemini 3 (최상)** | **Gemini 3 (최상)**      |
| **복원 기술** | OpenCV (낮음)                  | LaMa (최상)              | OpenCV (낮음)       | **LaMa (최상)**          |
| **인프라**    | CPU 가능                       | **GPU 필수**             | CPU 가능            | **CPU 가능 (최적화)**    |
| **비용**      | 무료                           | 높음 (GPU 서버)          | 저렴 (API)          | **저렴 (API + 무료)**    |
| **품질**      | 낮음                           | 높음                     | 보통                | **최상**                 |

### 2.2 선정 이유

1.  **비용 제로의 혁신**: 값비싼 GPU 인프라를 당장 도입하지 않고도, 수학적 알고리즘(OpenCV)에서 생성형 AI(LaMa)로 기술 패러다임을 전환할 수 있습니다.
2.  **검증된 성능**: 감지 영역은 이미 세계 최고 수준(Gemini)이므로 건드릴 필요가 없습니다. 오직 '지우는 붓'만 더 좋은 것(LaMa)으로 바꾸는 전략입니다.
3.  **리스크 최소화**: CPU 버전으로 품질을 먼저 검증한 후, 속도가 정 아쉬우면 그때 GPU를 도입해도 시스템 구조는 바뀌지 않습니다. (모델 파일만 교체하면 끝)

---

## 3. 기술적 실행 계획 (Step-by-Step)

### Phase 1: LaMa 모델 준비 및 환경 구축

- **목표**: `LaMa` 모델을 파이썬 환경에서 CPU로 구동할 수 있도록 준비.
- **세부 작업**:
  1.  **모델 확보**: `big-lama.pt` (PyTorch 원본) 또는 `lama_fp32.onnx` (CPU 최적화 버전) 다운로드.
  2.  **OnnxRuntime 도입**: PyTorch보다 CPU 추론 속도가 빠른 `App.py` 환경에 `onnxruntime` 라이브러리 추가.
  3.  **단위 테스트**: 샘플 이미지와 마스크를 넣어 배경이 지워지는지 확인하는 독립 스크립트 작성.

### Phase 2: Hybrid 파이프라인 통합

- **목표**: `src/image_processor.py`의 `create_clean_background` 메서드를 개조.
- **세부 작업**:
  1.  **마스크 생성 로직 개선**: Gemini가 감지한 좌표(`layout_data`)를 기반으로 마스크를 그리는 로직은 유지하되, LaMa 입력 규격(512x512 배수 등)에 맞춰 리사이징하는 전처리 로직 추가.
  2.  **Inpainting 엔진 교체**: 기존 `cv2.inpaint` 호출부를 `run_lama_inference` 함수로 대체.
  3.  **후처리**: LaMa가 생성한 결과물을 원본 해상도로 복원하여 저장.

### Phase 3: 최적화 및 안정화

- **목표**: CPU에서의 느린 속도를 보완하고 에러를 방지.
- **세부 작업**:
  1.  **Resize 전략**: 4K 이미지를 그대로 넣으면 CPU가 멈출 수 있음 -> 1024px 또는 2048px로 다운샘플링하여 처리 후 업스케일링하는 전략 적용.
  2.  **타임아웃 처리**: 사용자가 무한정 기다리지 않도록 비동기 작업 처리(이미 `BackgroundTasks` 적용됨).

---

## 4. 예상 위험 요소 및 대응

- **위험 1: 속도 저하**
  - **상황**: 고해상도 이미지 처리 시 1장당 30초 이상 소요될 수 있음.
  - **대응**: `1024px` 리사이징 옵션을 기본값으로 설정하여 속도와 품질의 타협점 탐색. (PPT 배경으로는 1024px도 충분함)

- **위험 2: 메모리 부족 (OOM)**
  - **상황**: 동시 접속자가 많을 경우 RAM 부족 발생.
  - **대응**: `app.py`의 `semaphore` 설정을 조정하여 동시 처리 작업 수를 제한.

## 5. 결론

이 계획은 **"추가 비용 없이 품질을 극대화"**하는 가장 합리적인 접근법입니다. 사용자는 기존 시스템 그대로 PDF를 업로드하면 되며, 내부 엔진(Engine)만 교체되어 훨씬 더 깨끗한 결과물을 받아보게 될 것입니다.

승인해주시면 즉시 **Phase 1 (모델 확보 및 단위 테스트)**부터 착수하겠습니다.
